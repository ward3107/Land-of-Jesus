# Internationalization & RTL

MVP UI languages: **Arabic**, **Hebrew**, **English**. Arabic and Hebrew are
right-to-left and get full RTL support.

## Two kinds of localization

1. **UI chrome** — buttons, labels, navigation. Lives in
   `packages/i18n/src/messages/{ar,he,en}.json`, looked up via
   `translate(locale, key)` / `createTranslator(locale)`. A test asserts every
   locale has the **same key set** as English, so missing translations fail CI.
2. **Organization content** — a message can carry multiple language variants
   (`message_translations`). At delivery, `selectTranslation` routes each
   subscriber to their preferred locale, falling back to the message's default
   locale, then to the first available variant. **Machine translation is never
   auto-published** (planned later, human-in-the-loop).

## Direction

`@communitydirect/core` owns the canonical locale primitives:

- `SUPPORTED_LOCALES`, `DEFAULT_LOCALE`, `normalizeLocale`
- `getDirection(locale)` → `'ltr' | 'rtl'`, `isRTL(locale)`

Web: the admin sets `<html lang dir>` from the active locale
(`htmlLangAttributes`), and Tailwind logical properties (`border-e`, `ps-*`,
`me-*`) flip automatically. Physical fallbacks use `physicalSide('start', locale)`.

Mobile: `applyLocaleDirection(locale)` toggles React Native's `I18nManager`
(`allowRTL`/`forceRTL`); a direction change requires an app reload, so the UI
prompts the user to restart.

## Adding a locale

1. Add the code to `SUPPORTED_LOCALES` (and RTL set if needed) in
   `packages/core/src/locales.ts`.
2. Add `packages/i18n/src/messages/<code>.json` with the full key set.
3. The key-parity test enforces completeness.
